# 全体構成と役割分担

最終更新: 2026-09-13

## 目指していること

**スマートフォンの Gemini に「ここを直して」と話しかけるだけで、改修から公開まで終わる。**
利用者の操作は承認のタップ1回だけ。スクリプトの手動実行はしない。

背景には「Claude Code の使用上限にすぐ達するので、擬似 Claude Code を Gemini Spark で
再現したい」という動機がある。Gemini を書き手、MCP を道具、Claude Code を検査役とする分担。

## 3つの道具の役割

| 道具 | 役割 | 実体 |
| --- | --- | --- |
| **Gemini Spark** | 話し相手。コードを書く | Connected Apps から MCP を呼ぶ |
| **App Studio** | GitHub / Pages / 承認などの面倒な処理 | Cloud Run 上の MCP サーバー |
| **Claude Code** | 検査役。セキュリティを含むレビュー、複雑な改修 | このセッション |
| **App Refiner** | 見て判断する場所（将来：承認コンソール） | GitHub Pages 上の単一HTML |

想定する流れ:

```
1. App Studio でアプリの骨格を作り、GitHub と Pages を用意する
2. Claude Code で育てる（複雑な仕様はここ）
3. 以降の細かい改修は Gemini から。承認タップだけで公開まで
4. Gemini が入れた変更は git のコミットとして残るので、
   あとから Claude Code が差分でレビューする
```

## なぜ「単一HTML」なのか

**ファイルが1個という意味であって、機能の制約ではない。**

App Refiner 自身が証拠になる。`index.html` 1ファイルで 1,914行・61関数・画面3つ・
ダイアログ3つ。タブ切り替え、iframe プレビュー、localStorage 永続化、検索、
JSONインポート/エクスポートまで入っている。

本当の限界はサーバーが無いことで、「その端末で完結するアプリ」は何でも作れるが、
「複数人・複数端末でデータを共有するアプリ」は作れない。
Firebase を足すとその限界が消える（後述）。

## セキュリティの考え方

### 危険の正体はプロンプトインジェクション

AI が間違えるという話ではない。**Gemini は外部の文章を読む**ので、その文章に
指示が仕込まれていれば、意図しないコードが生成されうる。これは Claude Code にも
同じく当てはまる（リポジトリやウェブページを読むため）。

そして **44KB のHTMLをスマホで読んで安全か判断することはできない。**
素朴に承認を挟んでも「押すだけ」になり、承認として機能しなくなる。

### だから防御は「読ませる」ではなく「封じる」

App Studio は公開するHTMLの `<head>` 直後に CSP の meta タグを差し込む
（`core/htmlaudit.py` の `harden()`）。

```
connect-src 'none'   →  fetch / XHR / WebSocket / sendBeacon / EventSource が全部止まる
```

実施するのはブラウザなので、生成側が何を書いても外へは出られない。
`audit()` は説明のための機能であって防御ではない（難読化を見落とすことが
テストで明示的に固定されている）。

### Firebase を使う場合は、防御の置き場所が移る

Firebase は外部通信そのものなので、CSP で止めたら動かない。
**その代わり、データを守るのは Firestore のセキュリティルールになる。**

| | CSP | Firestore ルール |
| --- | --- | --- |
| 守る対象 | 外に出さない | 誰が何を読み書きできるか |
| 書く場所 | HTML の中（毎回生成される） | Firebase 側（一度決めたら固定） |
| テスト | ブラウザで試すしかない | 専用のテストが書ける |
| レビュー | 毎回 86KB を読む | 短いルールを1回読む |

ルールが正しければ、コードを誰が書いても被害は限定される。
逆にルールが緩ければ、CSP をどれだけ厳しくしても守れない。
**「弱くなる」のではなく「チェックできる場所にチェックが移る」。**

## 決定事項（2026-09-13）

App Studio の `publish_custom_html` について、利用者の判断は次のとおり。

1. **ツールとして公開する** — はい
2. **CSP を緩める経路** — 引数として用意する。ただし既定は `STRICT_PUBLISH_CSP` のまま
3. **サイズ上限** — 256 KiB（現状の最大アプリが 86KB なので約3倍の余裕）

```
publish_custom_html(repo, html_content, title, commit_message, allow_connect=[])
                                                               ^^^^^^^^^^^^^^^^
                                            既定は空 = 外に一切通信しない
```

`harden(source, *, csp=...)` が既に差し替え可能な形になっているため、
選択肢2（Firebase 等の許可）は同じ設計の延長で実現できる。作り直しは発生しない。

**承認画面への要件**: `allow_connect` が空でないときは、それを目立つ位置に出すこと。
空なら「外に一切通信しない」が保証だが、緩めた瞬間にその保証は消える。
利用者がその変化に気づけないと、承認の意味が変わったことが見えない。

## 作業の分担

| 対象 | 担当 | 理由 |
| --- | --- | --- |
| App Studio 本体 | **App Studio 側のチャット** | 540件のテストを持つ当事者。並行作業中 |
| App Refiner | このセッション | |
| 生成物のレビュー | このセッション | `.claude/skills/review-published-app/` を参照 |

**App Studio のコードをこのセッションから変更しない。** ブランチを分けてもCloud Runの
サービス本体・Secret Manager・`app-studio-state` は共有であり、
何より同じ機能を二重に実装する無駄が生じる。
